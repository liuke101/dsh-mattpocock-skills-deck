# 检查同票写互斥

## 它守的是什么

这个仓库允许不同票、不同仓的写全并行，但**同一张票**的写必须一笔一笔来：改标签是「先读回、再整批替换」，改进度是「先读旧正文、再回写」，补边是「先预检、再写」。两笔同时进就会丢掉其中一次改动（#1040 就是为此加的这把锁）。

这条技能守的性质只有一句：**同一把锁键上，任意时刻最多只有一笔写在自己的 fn 里。** 附带两条：回超时的那一笔从未进入 fn；所有写结算之后锁表回到空。

一件事说清楚代价：互斥一旦被打破，用户看到的是「刚改的标签/状态/关系没了」，而且没有任何报错——两笔写都以为自己成功了。

## 当前的结果：红，且是真缺陷

在提交 `7be6c68b07eb81b108ce0f6584b7bfaf12dbe3ce` 上跑，检查失败，最短反例是 4 个事件：

1. 第 1 笔开始写，拿到锁，进入 fn 并一直执行；
2. 第 2 笔开始写，排在它后面等锁；
3. 第 2 笔等锁到上限，放弃等待；
4. 第 3 笔开始写，**直接进入 fn**，与仍在执行的第 1 笔同时运行。

原因在 `src/deck/shell/write-mutex.ts` 的超时分支（约第 89–94 行）：等待者超时后立刻放行自己那道门，并把自己从锁表摘掉。可是它放行的不是「下一位可以接管」，而是「下一位可以越过仍在执行的持锁者」——排在第 2 笔后面的写会当场进入，后来的新写也会因为锁表已被摘空而从一条新链开始。

这不是检查过严：把超时分支改成「等真正的前一位放锁之后再放行后继」，同一份检查会通过（123 次重放、71 个状态、最深 6 个事件）。也就是说，它分得开「真缺陷」与「检查写错了」。

**不要为了让这扇检查变绿去放宽判据。** 当前红色是它要报的结论。

## 怎么跑

在仓库根目录：

```
node --import ./scripts/ts-hook.mts .claude/skills/verify-write-mutex/check.ts
```

- 退出码 0：判据全部成立；打印重放次数、状态数、覆盖深度。
- 退出码 1：找到反例；按事件顺序打印最短的那一串，并指出反例发生在第几步。
- 首次在新工作区跑之前先 `pnpm install`（`prepare` 会生成 `src/shared/time-config/src/values.ts`）。如果报 `Cannot find module '.../time-config/src/values.js'`，跑 `node scripts/generate-time-config.mts` 补上，这不是检查本身的问题。
- 本仓的开发链要求 Node 24.15 及以上；检查与其它门禁同一口径。

检查不需要额外依赖，不联网，通常不到一秒。

## 覆盖范围

| 覆盖的代码 | 覆盖到的东西 |
| --- | --- |
| `src/deck/shell/write-mutex.ts` | 整个模块：`withKeyLock` 的排队、超时、放锁，以及 `keyLockSnapshot` |
| `src/deck/shell/capped-wait.ts` | `withCap` 的「真结果与等待口竞速」这一段，因为它决定了一笔到底是拿到锁还是超时 |

**没有覆盖**：fn 内部的读改写逻辑（标签、状态、边各自怎么读写）、真实时钟（超时由检查显式触发）、跨进程（锁表只在单个 Node 进程里）、调用方（`issue-patch*.ts`、`map-link.ts`）的装配与错误处理。

检查的边界写在 `check.ts` 顶部：最多 3 笔写、最多 6 个可控事件。结论只在这个范围内成立。

**这份检查确认时对应的代码版本**：`7be6c68b07eb81b108ce0f6584b7bfaf12dbe3ce`（2026-11-05，`write-mutex.ts` 自身最后一次改动是 `df4b9bb`，`capped-wait.ts` 是 `8eac117`）。

## 改动之后要不要重跑

先看被覆盖的代码有没有变：

```
git log --oneline 7be6c68b07eb81b108ce0f6584b7bfaf12dbe3ce..HEAD -- src/deck/shell/write-mutex.ts src/deck/shell/capped-wait.ts
```

- 没有任何输出：检查仍然描述当前的代码，按需跑一次即可。
- 有输出：先读 diff，再跑检查。确认检查仍然描述新代码之后，才把上面这一行的基准提交换成新的 `HEAD`；**不要只改提交号不读 diff**。如果新代码改变了事件形状（例如多了重入、多了取消、超时改由别处触发），先改 `check.ts` 里的事件与判据，再移动基准提交。

## 看到红色时

1. 先按打印的事件序列手工复述一遍：每一步在代码里对应哪一行、哪一次状态变化。复述不通，说明是检查自己错了（事件顺序不可能，或状态观察漏了），去修检查。
2. 复述得通，就是被检查代码的真缺陷。把反例按代码里的词写进手头的票或交付说明，**不要**顺手改产品代码去换绿色——是否修、怎么修由人决定。
3. 检查自己崩溃（打印「检查自身出错」）与判据失败是两回事：前者是检查或环境的故障，后者才是代码的结论。

## 需要更新检查时

- 加宽范围（更多写、更多事件）：改 `check.ts` 顶部的 `CLIENT_COUNT`、`MAX_EVENTS`，先量一次运行时间再提交；状态空间是指数增长的。
- 代码里新增了一类事件（取消、重入、优先级等）：在 `check.ts` 里同时补「事件怎么施加」「它怎么改变可见状态」「它是否进入 `stateKey`」三处，漏掉任何一处都会让去重把不同的未来当成同一个状态，从而漏报。
- 判断一个改动是否「有意」：以代码注释里写下的约定为准；约定本身变了，先改注释再改检查。
- 改动完成后，按上一节把基准提交移到确认时的新 `HEAD`。

需要把这套检查重新对齐到一次较大改动之后，或者要换一个目标重新做形式化验证，用 `/pstack:maintain-formal-verification-skill`。
